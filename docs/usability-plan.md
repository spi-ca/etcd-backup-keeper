# CLI 사용성 개선 계획 (과거 기록)

**보관 문서:** 아래는 MVP 이후 네 단계 구현 당시의 계획·검증 기록이다. 현재 작업 상태,
미완료 TODO, 배포 승인 또는 최신 릴리스 상태를 나타내지 않는다. 당시의 커밋·푸시·미실행
검사에 관한 표현도 그 시점에 한정한다. 현재 사용법은 [빠른 시작](quickstart.md),
계약은 [운영 안내](operations.md), 후속 릴리스 검증은 [요구사항 기록](requirements.md)을 따른다.

당시 상태: 네 단계 구현·관련 검사·검토 완료, 해당 작업 시점에는 커밋·푸시 미수행.

MVP 이후 개선은 기존 백업 안전성을 유지하면서 최초 실행과 장애 대응을 쉽게 만드는 데 집중한다.
사용자가 승인한 TODO 순서대로 구현하며, 기존 설정값·인증/CA 정책·스케줄은 변경하지 않는다.
커밋·푸시·PR·릴리즈·운영 endpoint 접근은 이번 구현 범위가 아니다.

| TODO | 순서와 범위 | 완료 기준 |
|---|---|---|
| #9 | `backup --verbose` 진행 로그와 README 가독성 | 실제 후보/수신/검사/확정/정리 단계, 전송량과 경과시간. stderr 전용·빈도 제한·비밀 비노출, 기존 JSON/비verbose 결과 유지. README를 첫 실행 중심으로 정리 |

| #11 | status·명령별 help·빠른 시작 | 사람용 단위/시각/age/미완료 안내 개선, status는 무결성 검사 아님을 명시, JSON 계약 유지, 첫 실행 문서 흐름 정리 |

## 구현 원칙

- 한 번에 하나의 작업만 진행한다. 완료된 작업의 핵심 근거는 이 문서에 남기고 TODO 목록은 정리한다.
- 진행 로그는 endpoint 원문·인증 정보·원시 외부 오류를 포함하지 않는다. 진행률·ETA를 추측하지 않는다.
- 로그 추가가 snapshot 스트림·검사 helper·잠금·sync·확정·retention 순서를 바꾸지 않는다.
- 각 작업 후 변경에 직접 관련된 테스트와 필요한 회귀 검사만 수행한다. 실제 확인하지 않은 성공은 주장하지 않는다.
- 신규 설정 키나 기본값 변경이 필요하면 구현 전에 사용자 승인을 받는다.
- `check` 성공은 snapshot 권한·정전 내구성·복원 성공·실제 systemd sandbox 적합성의 보증이 아니다.
- 실제 대상 Ubuntu의 서비스 실행과 정식 배포·릴리즈는 별도 작업이다.

## 진행 근거

- 시작 기준: 기존 MVP 커밋 `3b611e3`, 작업 트리 깨끗함 확인.
- #9: 구현·문서 반영 및 검토 완료. `--verbose`가 실제 후보/시도/전환, 수신량,
  체크섬·검사·확정·동기화·정리를 stderr에 표시한다. 수신량은 약 1초 간격 및 종료 시
  표시하며, read가 막힌 동안 별도 heartbeat를 보내지는 않는다.
- 작업자가 수행한 관련 backup/CLI 단위 테스트·vet·진행 로그 대상 race 테스트 통과.
  fake clock으로 빈도 제한을 검사했다. JSON 분리, 비밀 비노출, 출력 실패 시 엔진 계속
  실행 및 엔진 오류 우선순위도 검사했다. 이미 통과한 동일 검사는 반복하지 않았다.
- README를 128줄에서 99줄로 정리하고 소스 빌드 예시 경로를 통일했다.
  기존 상세 운영·복원·검증 문서로 연결하며, 통합 후 상대 링크와 shell 문법을 확인했다.
- 진행 로그의 현재 코드에 대한 독립 검토에서 구체적 회귀 결함은 발견되지 않았다.
  부모가 기준 커밋과의 diff를 확인했으며, 확정·동기화·정리 순서 변경은 없다.
- #10: 사람용 정적 오류별 hint와 확정 후 실패 안내를 구현·검토했다. JSON은 변경하지
  않았다. 새 복구 안내·입력 비노출·기존 사용법·진행 로그 오류 우선순위 관련 테스트와
  CLI vet가 통과했다. 안내의 short write를 발견해 수정 후 관련 검사를 재실행했다.
- #11: 사람용 상태에 IEC 크기·UTC 완료 시각·경과 시간·미완료 주의 표시와 무결성
  미검사 안내를 추가했다. 시간은 테스트에서 주입하며 미래 시각은 clock skew로 표시한다.
  명령별 도움말과 기존 JSON/offline 계약, 관련 기존 사용법 검사를 통과했다. 부모가
  코드·운영 안내를 검토했다. README에는 명령별 도움말 사용 안내 한 줄만 추가했다.

- #12: 기본 오프라인 `check`와 명시적 `--connect`를 구현했다. 새 check 패키지,
  읽기 전용 저장 경로, 새 명령 및 영향받는 도움말/offline CLI 테스트와 대상 vet를 통과했다.
  외부 endpoint나 실제 인증서 생성 없이 fake probe와 임시 파일로 검사했다.
- 새 정적 CLI 빌드와 실제 실행 파일의 `version`·`check --help`가 성공했다.
  변경한 README·운영 안내·계획 문서의 상대 링크와 shell 문법도 확인했다.
- 독립 최종 검토에서 새 점검 경로의 구체적 결함은 발견되지 않았다. 기본 오프라인,
  파일 무변경, 연결 제한시간과 정리, 신원 점검, 비밀 비노출 및 문서의 보장 한계를 검토했다.
- `--connect`는 모든 후보를 점검하므로 하나라도 접속/신원/지원 버전 확인에 실패하면
  실패한다. 이는 한 후보로 성공할 수 있는 실제 backup failover 동작과 다르다.
- 이번 후속 변경의 실제 인증된 원격 연결 시간 경계, 전체 etcd 통합·패키지·hosted CI는
  재실행하지 않았다. 이전 MVP CI 성공과 구분하며 배포·릴리즈 검증으로 확대하지 않는다.

## 실행 전 점검의 설계 경계

- `check`는 기본 오프라인이다. 설정과 명시된 인증 자료의 읽기/파싱, 저장 경로와
  권한을 점검하되 디렉터리·잠금·스냅샷 생성, sync 실험, 권한/CA 변경을 하지 않는다.
- 아직 생성되지 않은 최종 백업 디렉터리나 확인하지 않은 쓰기/내구성 조건을 실패 또는
  준비 완료로 단정하지 않는다. 확인됨·미확인·실패를 구분한다.
- `--connect`를 명시했을 때만 후보별 Status 연결과 지원 버전·클러스터 신원을 점검한다.
  스냅샷 요청은 하지 않으며, 원격 점검 성공도 snapshot 권한이나 복원 가능성의 증명이 아니다.
- 기존 `status`/`verify`는 계속 인증 자료도 읽지 않는 오프라인 명령이다. `check`만의
  새 결과를 기존 JSON envelope에 담고 기존 명령의 JSON 필드는 바꾸지 않는다.
